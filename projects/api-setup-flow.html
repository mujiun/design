Context

120k developers and partners build their products with the WhatsApp API — a critical segment that powers 80% of WhatsApp revenue. Before they can send a single message, they have to complete a multi-step API setup.

Discover Problems

The setup was challenging — only 3.5% of developers finished it. The pages were confusing on:

  • Developer vs. partner docs — unclear which applied to you
  • Setup sequence — no clear order to the steps
  • Required vs. optional — hard to tell what you actually needed

Result: low completion rate (3.5%), long completion time (2–4 weeks), low guidance satisfaction.

Define Scope

To lift completion, I had to answer two questions:

  • Which flow do we build first? The full journey was too big for an MVP.
  • How should the pages be organized? The old structure didn't match how users think.

Scoped with Engineering

I reviewed the full journey and pages, then narrowed to two flows given system constraints. With the team, I chose the developer flow (P0) — weighing build effort, impact, and revenue risk — and deferred the partner flow.

Restructured the Information Architecture

The old pages were grouped by the system's architecture — account settings vs. environment (server-side) settings — so completing a single goal meant jumping across pages. I regrouped them around the user's mental model: try first, then commit.

Shape Solutions

Where I Focused

I invested the most design time in the pages that shaped the whole experience — the left navigation, the landing page, and the two setup pages.

Left Navigation

A new nested menu so users see their full path upfront — the two paths and the required pages, in order.

Landing Page — Overview

90% are first-time, often non-technical users. Instead of a wall of options, I gave them two things: a linear guide (sequence, outcomes, time estimates) and an asset map (the tools and docs they'll need, and how they connect).

Discarded the common pattern of showing the linear guide and tool hub together — it overwhelmed the landing page.

Setup Page #1 — Try First

Users try before committing: claim a test number, run the sandbox, and mirror the official webhook flow. Claiming a test number before production setup rose from 15% to 62%.

Clarified the step for test number claim and send message.

Setup Page #2 — Production Setup

Users complete four tasks on one page — webhook, register phone number, add payment, and test integration — with defaults and auto-subscribe to reduce effort. With the clearer setup step, phone-number registration rose from 47.2% to 69.2% (+46.6%).

Grouped all tasks for production setup in one page instead of multiple pages.

Phone Number & Payment

Weighed combining vs. separating the phone-number and payment steps, and chose the layout that kept the page scannable without adding drop-off.

Permanent Token

The generate-token step was a common failure point — so I pushed engineering to build a one-tap solution.

Learning

Matching the interface to the user's mental model — not the system's architecture — is what unlocked completion. Reorganizing the same setup around what users are trying to do (try first, then commit) moved the numbers more than any single screen.
